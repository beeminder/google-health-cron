1. Tokens

You're right: Google has no personal access tokens, so each user has to create their own OAuth client in Google Cloud. That turns out to be the good option:

  • If Beeminder shipped one shared client, it would be Beeminder's app. All Google Health scopes are "Restricted", so going past 100 users means Google's verification plus a yearly outside security audit. That's the cost of the official integration, not of a DIY script.

2. Beeminder API hygiene

  • One datapoint per goal per day. The requestid is googlehealth-<datatype>-<YYYYMMDD>, sent through create_all, so a growing step count updates today's datapoint instead of adding a new one.
  • No Beeminder call when nothing changed. A local cache remembers what was last sent for each day, and a run only posts days whose value changed. One test runs the sync 720 times with no new data and checks that it made exactly one Beeminder call (and one Google token refresh).
  • The cache is only a speed-up. I checked the server code in working-clones/b2. Resending an identical datapoint comes back as a "Duplicate request" error with HTTP 200, and create_all skips the graph refresh when nothing changed. So the script treats those errors as success, and any other error fails loudly and gets retried on the next run.
  • Two server quirks the code works around:
  • Comments are compared as dp[:comment].to_s != dat.comment, so a resend with no comment never counts as a duplicate ("" != nil). It would update and regraph every time. The script always sends the same non-empty comment.
  • If both are sent, timestamp overrides daystamp, so the script sends only daystamp. Google already splits days by the user's local calendar day.
  • I didn't use diff_since/skinny. The sync never needs to read anything from Beeminder, and no read is cheaper than a skinny read. Where they'd help is noticing that someone edited or deleted the script's datapoints on the website. But the obvious check (watching the goal's updated_at) would also go off after the script's own writes trigger a graph refresh, and it costs a request every run to catch something rare. For now, such edits get overwritten only when that day's Google value next changes, or when the cache file is deleted. If you want the check anyway, it's easy to add.

Enough on the Google side. Before answering, I'll check how Beeminder's existing Fitbit autodata handles sleep and activities, since that's the precedent users will expect.

Sleep

Google doesn't aggregate sleep to one per day. Each sleep is its own session data point, and a nap is a separate session, not added to the night. Each session carries:

  • summary.minutesAsleep (also minutesAwake, minutesInSleepPeriod, and per-stage minutes), all as int64 strings.
  • metadata.nap, true for short sleeps with no stages.
  • metadata.mainSleep, marking the longest sleep with stages; there's one per day.
  • A stable-looking name ID.
  • metadata.processed, which is false while stages are still being computed. So minutesAsleep can change after we first see it, which the upsert already handles.

There's no daily total for sleep: dailyRollUp doesn't cover it, and the reference has no sleep rollup type at all. Grouping into days is up to us.

Which day a sleep belongs to: you can only filter sleep by end time, so it lands on the date you woke up. That's the old Fitbit dateOfSleep convention. "Tuesday's sleep" is Monday night plus any Tuesday nap. For sleep, list doesn't support filtering by data source and the docs send you to reconcile, which merges overlapping logs from different devices into one record.

What Beeminder does today: I checked lib/fitbit.rb. The hours_slept metric posts one datapoint per day, summary.totalMinutesAsleep / 60 for that date. The old Fitbit summary added up every sleep log for the date, so naps are already counted in the total.

My recommendation: keep sleep in the per-day shape. Add up minutesAsleep across the sessions ending each day, convert to hours, and keep one requestid per day. That matches what current Fitbit users get. It also fixes itself when sessions get merged or split: Fitbit does split a night into two when you wake in the middle, and users edit sleeps. Per-session datapoints would leave orphans in those cases.

The real question is naps. "Sleep 7 hours a night" goals arguably shouldn't let a nap count. If you want that, I'd add it as a second metric (main sleep only) rather than a setting. Bedtime and wake-time metrics would only make sense for the main sleep anyway.

Activities

Yes, the exercise data type exists. Each workout is its own data point with:

  • name, an ID for the session.
  • exerciseType, an enum of about 100 values (RUNNING, WALKING, BIKING, …).
  • Civil start and end times.
  • activeDuration, the duration excluding pauses.
  • metricsSummary, with distanceMillimeters, caloriesKcal, steps, and average pace and speed.
  • dataSource.recordingMethod: MANUAL, ACTIVELY_MEASURED, PASSIVELY_MEASURED, DERIVED or UNKNOWN.

There's no daily rollup for exercise either. You filter by civil start date, and a page holds at most 25 results, so the script needs paging. Fitbit's auto-detected walks can add up.

I agree that multiple runs should mean multiple datapoints, and Beeminder already has precedent. lib/strava_goal.rb posts one datapoint per activity, keyed by strava_id. It filters by activity type, uses a 7-day window, and the value is distance, duration, moving time, calories, or 1 for a count. (Beeminder's Fitbit "activities" metric goes the other way: one count per day.) In the script, the requestid would be built from Google's session ID, so each run upserts its own datapoint and a do-more goal sums them.

Caveats with sessions that daily totals don't have:

  • Orphans: if someone deletes a duplicate or bogus auto-detected session in the Fitbit app, its Beeminder datapoint stays and inflates the total. The Strava integration has the same gap. Fixing it means storing the Beeminder datapoint ID from the create_all response in the cache, and deleting datapoints whose session disappeared within the window. That's destructive, and a glitch in Google's list (say, a paging bug) would delete real data, which the next run would then recreate. My lean is to match Strava for now and not delete.
  • ID stability: whether these IDs stay the same between calls needs a real account to check. For raw list they should, since they're stored IDs. For reconcile the docs don't say. Raw list could count a run twice if two devices recorded it, so I'd start with list and check.
  • Dating: I'd date a run by its civil start, since that's what Google filters on. Strava's integration uses end time, though a comment there points to issue #1810 about switching to start.

This is a small change: the cache and requestids would be keyed by requestid instead of by date. Per-day metrics (steps, sleep) use the date in the requestid, and session metrics use the session ID. Everything else stays: the 7-day window, sending only what changed, and treating duplicates as success.

Why Testing mode breaks after 7 days. Google issues two tokens:

  • An access token lasts about an hour. The script gets a new one automatically from the refresh token, and that part keeps working.
  • The refresh token has a fixed lifetime. In Testing it expires 7 days after it was issued, no matter how often it's used. Google's docs: a Testing-status project "is issued a refresh token expiring in 7 days," unless the only permissions requested are basic profile info.
